# UP — Milestone 1

Bluetooth-first proximity discovery. This milestone is the **complete UI with
mock data**: every screen, both languages, both themes, the full Live → UP →
Match → Chat → Reality Check flow — and no backend and no real BLE anywhere in
it.

That boundary is deliberate. Nothing in this project pretends to be platform
behaviour that has to become real later.

---

## Run it

This repository contains `lib/`, `test/` and the project config. The `android/`
and `ios/` folders are generated by Flutter itself, so the first step creates
them.

```bash
# 1. Generate the platform folders next to the code
./setup.sh

# 2. Run on a connected device or simulator
flutter run
```

`setup.sh` runs `flutter create` into this directory (which only adds the
platform scaffolding — it never touches `lib/`), then `flutter pub get`.

If you would rather do it by hand:

```bash
flutter create --org co.vibit.up --project-name up --platforms=ios,android .
flutter pub get
flutter run
```

### iOS

```bash
open ios/Runner.xcworkspace     # set your team under Signing & Capabilities once
flutter run -d <your-iphone>
```

### Android

```bash
flutter devices                  # find the device id
flutter run -d <device-id>
```

### Checks

```bash
flutter analyze

```

**Heads up:** `flutter analyze` and `flutter test` have not been run against

**zero third-party dependencies** — everything it imports ships inside the
Flutter SDK, so `flutter pub get` has nothing to resolve and nothing to break.

Minimum: **Flutter 3.22 / Dart 3.4**.

## What you can do in the app

The demo sheet is reachable from the top of the Home screen. UP cannot be
judged alone — the product needs a second person in the room — so until real
BLE arrives, that sheet stands in for the radio and the server.

1. **GO LIVE** — pick 30 / 60 / 120 minutes first, then go live. The radar
   starts finding people on its own, roughly one every seven seconds.
2. **Nearby** — the grid of people who are also Live. No distances anywhere.
3. Open a profile → **UP** or **Pass**.
4. Demo sheet → *Someone sends you an UP* → their card gets an UP flag.
5. UP them back, or use *Force a match*, and the match screen fires.
6. Chat. After four messages the **Reality Check** appears by itself.
7. Settings → language, appearance, Live duration, block list, delete account.

The Live timer keeps running across navigation, and the session expires on its
own — the same code path as pressing STOP LIVE.

## Architecture

```
lib/
  core/
    l10n/          AppStrings (he + en) and a small Localizations wrapper
    theme/         palette, type scale, tokens, ThemeData
  domain/
    entities/      UserProfile, NearbyPerson, LiveSession, MatchThread, …
    repositories/  the four interfaces the backend will implement
  data/mock/       in-memory implementations of those four interfaces
  state/           ChangeNotifier controllers + AppScope (DI)
  ui/
    components/    the shared widget library
    screens/       one file per screen, tabs/ for the four shell tabs
    navigation/    named routes
test/              match logic, live session, app smoke test
```

Three rules the code follows:

**No business logic in widgets.** The match rule, the rate limit, the badge
threshold and the session expiry all live in `domain/` and `data/`. Screens read
state and call methods. That is why `test/match_logic_test.dart` can assert the
whole matching contract without touching the UI.

**The repository interfaces are the backend contract.** Every method in
`domain/repositories/` carries a doc comment naming the endpoint it becomes.
Milestone 2 writes HTTP implementations of those same four interfaces; nothing
above them changes.

**`PresenceRepository` is the only seam BLE will touch.** The app never sees a
token, a MAC address or an RSSI value — it asks to go Live and receives resolved
people. Keeping that boundary narrow is what makes the identity rules
enforceable in one place instead of scattered through the UI.

### No state-management package

`ChangeNotifier` + `ListenableBuilder` + one `InheritedWidget` covers everything
here. Adding Riverpod or Bloc now would be a preference to defend later rather
than a problem being solved. If you want one, it is a change to
`state/app_scope.dart` and the two extension getters at the bottom of it.

### No photo assets

Nobody's face belongs in a demo repo, and stock portraits make a prototype read
as further along than it is. Each person gets a deterministic three-colour aura
from their seed, so the same person always looks the same and the grid still has
colour and rhythm. `ui/components/aura_photo.dart` becomes an `Image.network`
with a signed URL in Milestone 2, and no call site changes.

### No custom fonts

Milestone 1 runs on the platform faces — SF on iOS, Roboto on Android — so there
is no font download and no asset step. The scale, weights and tracking in
`core/theme/typography.dart` are what carry the personality. Adding a display
face later is a change to `AppTypography.displayFamily` and a `pubspec.yaml`
assets block.

## What changed from the spec

Seven decisions differ from `UP_App_Master_Spec_Claude.docx`. Each one is
implemented, and each one is reversible.

| Area | Spec | This build |
|---|---|---|
| Distance | "at most *near you*" | Removed entirely. One tag: *near you right now*. `NearbyPerson` has no distance field to leak. |
| Incoming UP | "a gentle notification is possible" | Private model. You only learn someone UP'd you once you have also UP'd them. Less pressure, weaker harassment surface, stronger match moment. |
| Live duration | a timer | Chosen **before** going Live, not in settings. It is a decision made in the moment; burying it turns Live into an always-on switch. |
| Reality Check | its own screen | Arrives on its own after four messages. Nobody goes looking for a feedback form. Carries an explicit anti-rating line on screen. |
| Permissions | system prompt | A pre-prompt that explains first, including why Android may ask for location. The OS dialog is one-shot. |
| Age gate | a checkbox | Blocking. Both stores treat an unenforced 18+ claim on a dating app as a rejection. |
| Photo verification | badge after N answers | Rules moved into `RealityBadgeRules` so the app and the future server share one definition: minimum 3 answers, 70% positive, "kind of" counts as neutral rather than negative. |

## Three things that still need a decision

**1. iOS in the background.** A backgrounded iOS app moves its BLE
advertisement into the overflow area, where Android cannot see it at all.
iPhone↔Android discovery in the background is not reliable and no amount of
implementation effort will make it so. This build assumes **foreground-first**:
you open UP in the bar, you are Live. Any UX that depends on discovery while the
app is closed has to be designed out, not engineered around.

**2. Presence fallback.** At a party of two hundred, BLE alone will miss a large
share of the room. The proposal is coarse venue presence server-side —
a geohash at roughly 200–500m, never shown to the user, deleted when the session
ends — running alongside BLE rather than replacing it. This belongs in
Milestone 3 and it changes `PresenceRepository` only.

**3. Cold start.** UP works only when two people are Live in the same bar. That
is a launch problem, not a product problem, and it is the one most likely to
kill the thing: a nationwide release produces an empty app everywhere. One
campus, one festival, one street — saturate a single place first.
